# v0.13 — Resiliência, Performance e Load Testing

## Objetivo

Transformar a plataforma observável da v0.12 em uma plataforma capaz de se proteger de picos, saturação e falhas de dependências externas.

## Rate limiting

O middleware usa Redis e uma janela fixa atômica via Lua. Quando existe um JWT válido, o escopo é o `tenant_id`; para tráfego sem JWT, usa um hash do IP do cliente. Health, readiness, metrics e documentação ficam isentos.

Headers de resposta:

- `X-RateLimit-Limit`;
- `X-RateLimit-Remaining`;
- `X-RateLimit-Reset`;
- `Retry-After` em respostas HTTP 429.

Redis indisponível usa **fail-open** por padrão e registra o evento em métricas/logs.

## Bulkhead

Chamadas OpenAI passam por um `asyncio.Semaphore` por processo da API. O objetivo é impedir que excesso de chamadas LLM consuma toda a capacidade do worker e afete endpoints não relacionados.

## Circuit breaker

O estado é compartilhado via Redis, adequado a múltiplas réplicas da API:

```text
closed -> failure threshold -> open -> cooldown -> half-open probe -> closed/open
```

O breaker atua sobre falhas retryable do provider OpenAI.

## Retry

O SDK OpenAI já possui retry próprio. Por isso o retry externo da plataforma fica em **1 tentativa por padrão**, evitando retry amplification. A política pode ser aumentada para providers que não possuam retry interno.

## Load testing

`scripts/load_test_v13.py` mede:

- throughput em requests/s;
- min/avg/p50/p95/p99/max;
- error rate;
- distribuição de status HTTP.

Perfil padrão seguro:

```text
200 requests
20 concorrentes
/api/v1/users/me
```

Esse perfil não invoca LLM e não gera custo de OpenAI.

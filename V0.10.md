# v0.10 - Twilio Media Streams Bridge Lab

## Objective

Connect the existing Voice AI stack to a WebSocket endpoint that speaks the Twilio bidirectional Media Streams protocol and prove two transport behaviors locally:

1. Realtime PCMU audio is emitted as Twilio `media` messages and acknowledged with `mark`.
2. Caller audio arriving while assistant audio is playing triggers barge-in and a Twilio `clear` message.

## What is real in the smoke test

- FastAPI WebSocket endpoint.
- Twilio-compatible `connected`, `start`, `media`, `mark`, `clear`, `stop` messages.
- 20 ms PCMU / 8 kHz audio frames.
- LangGraph classification and tool execution.
- Tenant-scoped `check_price` lookup.
- Real OpenAI Realtime audio generation with `gpt-realtime-2.1`.
- Voice session/event persistence and bridge metrics.
- Barge-in cancellation of buffered outbound media.

## What is simulated

The Twilio side is a local protocol-compatible WebSocket client running inside the API container. No PSTN call or Twilio phone number is claimed in v0.10.

To keep the transport test deterministic, the local Twilio `start.customParameters` includes `lab_transcript`. Live inbound speech transcription / direct audio forwarding is a later integration step.

## Bridge protocol

Twilio -> server:

- `connected`
- `start`
- `media`
- `mark`
- `dtmf`
- `stop`

Server -> Twilio:

- `media`
- `mark`
- `clear`

Audio is raw `audio/x-mulaw`, 8000 Hz, mono, base64 encoded inside Twilio JSON messages.

## Barge-in

When an inbound `media` event arrives while assistant output is active:

1. the bridge sets an output cancellation flag;
2. sends Twilio `clear`;
3. stops sending remaining assistant audio frames;
4. persists `barge_in_count`, `clears_sent`, and interrupted status in session metadata.

## Security boundary

`VOICE_BRIDGE_LAB_TOKEN` exists only for deterministic local testing and must not be treated as Twilio production authentication. A real Twilio deployment must validate `X-Twilio-Signature` and use per-environment secrets.
